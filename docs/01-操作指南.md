# 操作指南

命令示例统一写作 `orc`，替换为你实际用的实现：

```bash
alias orc="node scripts/orchestrator.mjs"     # 或 alias orc="python scripts/orchestrator.py"
```

## 一次性准备

1. 目标项目已是 Git 仓库，主干受保护，集成分支名与 `agents.json.integrationBranch` 一致。
2. 建立应用结构，例如 `apps/api`、`apps/admin-web`、`apps/mobile`、`packages/shared-types`。
3. `docs/product.md` 写角色、业务流程、非功能要求；`docs/architecture.md` 写技术栈和模块边界。
4. 契约 Agent 先定 `spec/openapi.yaml`、数据库模型、共享类型、设计系统版本。
5. `control/ownership.json` 锁定每个 role 的 `paths`，并把契约/共享类型/迁移/CI 放进 `exclusive`。
6. `control/agents.json` 的 `verifyCommands` 换成项目真实命令（默认值会失败，这是故意的）：

```json
"verifyCommands": [
  {"command": "pnpm lint", "stopOnFail": true},
  {"command": "pnpm typecheck", "stopOnFail": true},
  {"command": "pnpm test -- --run", "stopOnFail": true}
]
```

7. `control/backlog.json` 写任务：每条必须有 `paths` 和 `acceptanceCriteria`，否则 `validate` 不过。
8. 跑一次 `orc validate`，把它接进 CI。

## 共享控制目录（必须）

多个 worktree 各有独立的文件副本，所以不能让每个 Agent 写自己那份 `control/backlog.json`：

```bash
orc init-runtime --path ../project-control-runtime
export AI_CONTROL_ROOT=/abs/path/to/project-control-runtime
```

`init-runtime` 会在仓库内留下 `control/RUNTIME.json` 指针（已被 `control/.gitignore` 忽略），所以忘记设环境变量时也能找到正确的控制目录。仍然建议在每个 Agent 的提示词里写死绝对路径。

任何写命令在检测到自己正操作仓库内的 `control/` 模板时会直接报错，不会出现"两份状态各写各的"。

## 每日运行

协调 Agent 每 15--30 分钟一轮：

```bash
orc coordinator-claim --agent coord-01
orc recover --stale-minutes 45
orc next
orc status
# ...分派...
orc checkpoint --agent coord-01 --summary "已派发 AUTH-010" --next-action "等待 CI"
orc archive --message "chore: 第 12 轮"
orc coordinator-release --agent coord-01
```

`next` 会同时给出被跳过任务的原因（依赖未合入 / 路径被占 / 等待审查 / 等待集成 / 等待人工裁决），队列停滞时先看这里。

Worker 在独立 worktree 执行：

```bash
git worktree add ../project-auth -b agent/auth-010 main
cd ../project-auth
export AI_CONTROL_ROOT=/abs/path/to/project-control-runtime
orc claim-task --task AUTH-010 --agent api-01
```

一轮工作的完整闭环：

```bash
# 1. 改代码，只改任务 paths 内的文件
git add . && git commit -m "feat(auth): implement phone login"

# 2. 用 Git 事实刷新 manifest（commit / changedFiles 自动填，别手写）
orc manifest --task AUTH-010

# 3. 跑校验，结果由工具写入 manifest.commands
orc verify --task AUTH-010

# 4. 填 acceptanceEvidence 每一条，写 handoff.md
#    位置：$AI_CONTROL_ROOT/artifacts/AUTH-010/<runId>/

# 5. 送审（不合格会明确列出每一条原因，任务保持 working）
orc complete --task AUTH-010 --agent api-01
```

Reviewer：

```bash
orc review --task AUTH-010 --agent reviewer-01 --result approve --note "CI 与验收通过"
# 合并 PR 后，在已同步集成分支的 worktree 里：
git fetch && orc integrate --task AUTH-010 --agent reviewer-01
```

`integrate` 会用 `git merge-base --is-ancestor` 确认提交真的进了集成分支，确认不了就拒绝。任务只有到这一步才变 `done`，下游依赖才解除。

## 常见拒绝与处理

| 报错 | 原因 | 处理 |
|---|---|---|
| `没有活动的协调器租约` | Worker 自作主张领任务 | 协调器先 `coordinator-claim`；单人模式设 `requireCoordinatorLease=false` |
| `worktree 有未提交改动` | 起点不干净 | 先提交或清理 |
| `commands 里没有 verify 记录的结果` | 手写了 `pass` | 跑 `orc verify --task <ID>` |
| `改动越界` | 改了任务 `paths` 外的文件 | 拆任务，或让协调器扩大 `paths` |
| `改动命中 role=... 的单写者专属路径` | 动了契约/迁移/CI | 交给 `contract-owner` 单独立任务 |
| `headCommit 等于 baseCommit` | 没提交就想送审 | 先 commit |
| `路径与活动任务冲突` | 两个任务会改到同一批文件 | 串行，或重新切分任务边界 |
| `依赖未完成（必须已合入集成分支）` | 依赖只审过没合并 | 先合并并 `integrate` |

## 桌面端 Agent 建议

- 协调聊天用一个长期存在的项目会话，只读任务、PR、CI 和工件，不写业务代码。
- 每个 Worker 一个独立会话 + 独立 worktree，提示词带任务 ID 和 `AI_CONTROL_ROOT` 绝对路径。
- 给协调会话设 20 分钟定时任务：`按 prompts/coordinator.md 执行一次协调周期。`
- 上下文压缩、会话结束或崩溃后，从 `AI_CONTROL_ROOT`、Git、PR、CI 和 `artifacts/` 恢复，不要人工重述历史。

## 人工队列

只看两处：`backlog.json` 里 `blocked` 的任务，和 `docs/decisions.md`。只裁决产品方向、风险操作和生产发布；普通编码、测试、审查不需要逐步确认。
