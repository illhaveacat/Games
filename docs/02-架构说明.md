# 架构说明

```text
                     人类：目标、边界、例外决策
                                  │
                         Coordinator（单实例，租约保证）
                 ┌────────────────┼────────────────┐
                 │                │                │
            任务状态机        worktree 分派      CI / PR / 工件
                 │                │                │
           API Worker       Web Worker       App Worker
                 └────────────────┼────────────────┘
                                  │
                         Reviewer / QA（独立，不可自审）
                                  │
                     集成分支（integrate 校验祖先关系）
```

## 持久化状态

| 位置 | 作用 | 谁可写 |
|---|---|---|
| `$AI_CONTROL_ROOT/backlog.json` | 任务、依赖、状态、分支、基线提交、审查、历史 | 只有状态机命令 |
| `$AI_CONTROL_ROOT/state.json` | 协调器租约、检查点 | 只有状态机命令 |
| `$AI_CONTROL_ROOT/agents.json` | 并发、租约时长、集成分支、校验命令、门禁开关 | 人 |
| `$AI_CONTROL_ROOT/ownership.json` | 路径归属与单写者路径 | 人 + contract-owner |
| `$AI_CONTROL_ROOT/artifacts/<task>/<run>/` | manifest、handoff、日志 | 该任务 Worker |
| `docs/progress.md` | 可读进度摘要 | 协调器 |
| `docs/decisions.md` | 必须由人裁决的事项 | 所有人可追加 |
| Git / PR / CI | 代码事实与自动验收 | 标准开发流程 |

工件放在共享控制目录而不是仓库里，有两个原因：Reviewer 不必切到 Worker 的分支就能看到证据；工件也不会混进业务 diff 触发越界检查。`archive` 命令给这个目录留 Git 快照，状态本身也有历史可查。

## 状态机

```text
ready ──claim──> working ──complete(证据门禁)──> review ──approve──> approved ──integrate(已合入)──> done
  ^                 │                              │                      
  │                 │                              └──reject──> rework ──claim──> working
  │                 │                                              │
  │                 └──租约超时/recover──> interrupted ──claim──> working
  │                                                                │
  └──────────────── unblock ──────── blocked <── block / 驳回超限 ──┘
```

- `working | review | rework | approved | interrupted` 都**持有路径锁**：分支还没合入，这些文件就不能被别的任务碰。
- `done` 只能由 `integrate` 产生，且必须通过 `git merge-base --is-ancestor <headCommit> <集成分支>`。
- 依赖只认 `done`。审查通过但没合并的任务不会解除下游依赖——否则下游 worktree 从集成分支切出来，根本没有那段代码。

## 门禁（工具强制，不是自觉）

| 门禁 | 位置 | 内容 |
|---|---|---|
| 分派门禁 | `claim-task` | 协调器租约存在、依赖已合入、路径不冲突、并发未超限、分支未被占用、worktree 干净 |
| 证据门禁 | `complete` | manifest 无占位值；`runId`/`agent`/`branch` 对得上；`commands` 必须含 `verify` 写入的结果且全 pass；每条验收条件有非空证据；`handoff.md` 已改写 |
| Git 门禁 | `complete` | base 是 head 的祖先、head 就是当前 HEAD、工作树干净、`changedFiles` 与实际 diff 一致 |
| 边界门禁 | `complete` | 改动文件 ⊆ 任务 `paths` ∩ 本 role 的 `paths`，且不得命中他人 `exclusive` |
| 审查门禁 | `review` | 只能审 `review` 状态；实施者不可自审 |
| 集成门禁 | `integrate` | 提交必须是集成分支的祖先 |
| 回路门禁 | `review` | 驳回次数超过 `maxReworkRounds` 自动转 `blocked` 交人，防止 Agent 无限返工 |
| 状态门禁 | 所有写命令 | 拒绝写仓库内 `control/` 模板，避免多 worktree 状态分裂 |

## 并发规则

1. Coordinator 单实例，靠共享控制目录里的租约保证。
2. Worker 并发受 `agents.json.maxConcurrentWorkers` 限制，`next` 和 `claim-task` 都会检查。
3. 两个活动任务的 `paths` 有交集时不可同时领取。冲突判定是**保守的**：`**` 两侧都带通配符时按冲突处理，宁可串行也不并发改同一批文件。
4. 契约、共享类型、数据库迁移、根依赖、CI 由唯一 `contract-owner` 串行处理，越界在送审时按实际 diff 拦截。
5. 每个 Worker 独立分支/worktree；同一分支不能被两个活动任务占用。

## 已知边界

- **路径冲突是保守近似。** `apps/**` 与 `**/util/**` 会被判为冲突，即便实际文件不重叠。宁可少并发，不要两个 Agent 改同一个文件。
- **越界检查看的是 `base..head` 的 diff。** rework 后重新 `claim-task` 会把基线重置到当前 HEAD，此前已通过检查的提交不会重复检查。
- **`verify` 用 shell 执行你配置的命令。** 命令内容是你自己的配置，不做沙箱。CI 里应当再跑一遍，本地 verify 只是送审的必要条件。
- **锁是文件锁。** 同机多进程可靠；共享控制目录放网络盘时，`O_EXCL` 语义可能不保证，请放本地盘。
- **两套实现必须一起改。** 改完跑 `node scripts/conformance.mjs`，它会逐步比对 Node 与 Python 的行为，不一致直接失败。
