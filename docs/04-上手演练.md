# 上手演练（30 分钟，手敲命令版）

> **不想敲命令？** 看 [05-人类使用手册.md](05-人类使用手册.md)——把开场白贴给 AI，之后只说人话就行。
> 这份文档是给想亲手摸一遍闸门、或者要排障的人看的。

用一个待办清单 demo 走完整流程：派发 → 开发 → 证据 → 审查 → 集成 → 中断恢复。

**每一步都标了【目录】，先 `cd` 到那里再执行。** 所有命令在 cmd、PowerShell、git-bash 里写法一样，一行一条，不要合并。

前提：装了 Node 18+ 和 Git。沙箱零依赖，不用 `npm install`。
下面的输出都是真实跑出来的，你应该看到几乎一样的内容（时间戳和 SHA 会不同）。

## 1. 看清楚这个项目

【目录：`orchestrator-demo`】

```
cd ..\orchestrator-demo
```

三个任务，三个角色，一条依赖链：

| 任务 | 角色 | 可改路径 | 依赖 |
|---|---|---|---|
| SPEC-001 定义契约 | contract-owner | `spec/**` | — |
| API-010 列表与新增 | api-worker | `apps/api/todos/**` | SPEC-001 |
| WEB-020 管理页渲染 | admin-worker | `apps/admin-web/**` | API-010 |

先体检控制面：

```
node scripts/orchestrator.mjs validate
```

```json
{ "controlRoot": "D:\\Project Code\\orchestrator-demo-control", "ok": true, "problems": [], "warnings": [] }
```

`controlRoot` 指向 `-control` 目录、`ok: true`，就说明环境对了。

> 如果 `controlRoot` 指向 `orchestrator-demo\control`，说明指针没生效——删掉两个目录重新跑第 0 步。

`validate` 查的是：任务 id 重复、状态非法、缺 `paths`/`acceptanceCriteria`、依赖指向不存在的任务、**依赖成环**、活动任务路径冲突、并发超限、角色路径越界。把它接进 CI。

【目录：`orchestrator-demo`】一个任务一个 worktree，不要在主目录里改代码：

```
git worktree add ..\orchestrator-demo-spec -b agent/spec-001 main
```

【目录：`orchestrator-demo-spec`】切过去领任务：

```
cd ..\orchestrator-demo-spec
```

```

```

```json

  "task": "SPEC-001",
  "runId": "run-20260922-044313-94b4f5",
  "branch": "agent/spec-001",
  "baseCommit": "665ec03...",
  "artifactDir": "D:\\Project Code\\orchestrator-demo-control\\artifacts\\SPEC-001\\run-20260922-044313-94b4f5",
  "acceptanceCriteria": ["spec/openapi.yaml 定义 GET /todos 与 POST /todos", "..."],
  "paths": ["spec/**"]

```

**把 `artifactDir` 记下来**，第 3.4 步要去那里填证据。

### 3.2 写代码

【目录：`orchestrator-demo-spec`】用编辑器新建 `spec\openapi.yaml`，内容：

```yaml
openapi: 3.0.3
info:
  title: 待办清单 API
  version: 1.0.0
paths:
  /todos:
    get:
      summary: 列出全部待办
      responses:
        "200":
          description: 待办数组
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/Todo"
    post:
      summary: 新增一条待办
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [title]
              properties:
                title:
                  type: string
                  minLength: 1
      responses:
        "201":
          description: 新增成功
        "400":
          description: 标题为空
components:
  schemas:
    Todo:
      type: object
      required: [id, title, done]
      properties:
        id:
          type: integer
        title:
          type: string
        done:
          type: boolean
```

提交（两条命令分开执行，别用 `&&`，PowerShell 5 不支持）：

```
git add -A
```

```
git commit -m "feat(spec): 定义待办清单契约"
```

### 3.3 故意犯错①：不跑 verify 直接送审

【目录：`orchestrator-demo-spec`】

```
node scripts/orchestrator.mjs manifest --task SPEC-001
```

```
node scripts/orchestrator.mjs complete --task SPEC-001 --agent contract-01
```

```
错误: 证据未通过，任务保持 working：
  - manifest.commands 为空：至少需要一条真实执行过的验证命令（测试 / verify）
  - commands 里没有 verify 记录的结果：请运行 `orchestrator verify --task <id>` 由工具写入真实退出码
  - 验收条件证据为空: spec/openapi.yaml 定义 GET /todos 与 POST /todos
  - 验收条件证据为空: todo 字段包含 id、title、done
  - 验收条件证据为空: verify 全部通过
  - handoff.md 与模板完全相同：未写入可接力的事实
```

这就是这套架构和"写提示词让 Agent 自觉"的区别：**它逐条告诉你差什么，任务停在 `working` 不动。**

### 3.4 正确的收尾

【目录：`orchestrator-demo-spec`】先跑校验，退出码由工具写进证据文件：

```
node scripts/orchestrator.mjs verify --task SPEC-001
```

```json
{
  "ok": true,
  "results": [ { "command": "node --test", "result": "pass", "exitCode": 0, "recordedBy": "verify" } ],
  "recordedInto": "D:\\...\\artifacts\\SPEC-001\\run-.../manifest.json"
}
```

然后**用编辑器打开 3.1 步那个 `artifactDir` 里的两个文件**，这是全流程唯一需要手写的地方：

**`manifest.json`** — 给每条 `acceptanceEvidence` 的 `evidence` 填具体位置：

```json
"acceptanceEvidence": [
  { "criterion": "spec/openapi.yaml 定义 GET /todos 与 POST /todos",
    "evidence": "spec/openapi.yaml:6-40 paths./todos 的 get 与 post" },
  { "criterion": "todo 字段包含 id、title、done",
    "evidence": "spec/openapi.yaml:42-53 components.schemas.Todo，required: [id,title,done]" },
  { "criterion": "verify 全部通过",
    "evidence": "node --test 退出码 0，见 commands[0]" }
]
```

`commands`、`changedFiles`、`baseCommit`、`headCommit` 已经自动填好了，别动。

**`handoff.md`** — 覆盖成你自己的内容，例如：

```markdown
# 交接记录

- 任务 / 运行编号：SPEC-001 / run-20260922-044313-94b4f5
- 分支与基线提交：agent/spec-001，665ec03 → 3de27e9
- 已完成的事实：
  - 新增 spec/openapi.yaml，定义 GET /todos 与 POST /todos（201 / 400）
  - Todo schema：id/title/done 三个字段均 required
  - POST 的 title 设了 minLength: 1，空标题按 400 处理——API-010 要实现这条
- 未完成的最小下一步：无，本任务已闭环
- 运行过的命令及结果：node --test → pass
- 修改的文件：spec/openapi.yaml
- 已知风险：未定义分页与排序
- 恢复指令：git switch agent/spec-001
```

判断标准只有一条：下一个 Agent 只看这份文件和 Git，能不能接着干。

送审：

```
node scripts/orchestrator.mjs complete --task SPEC-001 --agent contract-01
```

```json
{ "task": "SPEC-001", "status": "review", "headCommit": "3de27e9..." }
```

### 4.2 故意犯错③：没合并就想 done

【目录：`orchestrator-demo-spec`】

```
node scripts/orchestrator.mjs integrate --task SPEC-001 --agent reviewer-01
```

```
错误: 3de27e9642de 尚未合入 main：请先合并 PR 并在本 worktree 更新该分支（git fetch）
```

真实项目里这一步是"合并 PR → `git fetch`"。demo 里回主目录直接合。

【目录：`orchestrator-demo`】

```
cd ..\orchestrator-demo
```

```
git merge --no-ff -m "merge: SPEC-001 契约" agent/spec-001
```

```
node scripts/orchestrator.mjs integrate --task SPEC-001 --agent reviewer-01
```

```json
{ "task": "SPEC-001", "status": "done", "integrationBranch": "main", "mergeCommit": "c269520..." }
```

### 5.2 写代码

【目录：`orchestrator-demo-api`】新建 `apps\api\todos\todos.mjs`：

```js
// 字段以 spec/openapi.yaml 的 Todo schema 为准：id / title / done
const store = [];
let nextId = 1;

export function listTodos() {
  return store.map((todo) => ({ ...todo }));
}

export function addTodo(title) {
  if (typeof title !== "string" || title.trim() === "") {
    throw new Error("title 不能为空");
  }
  const todo = { id: nextId++, title: title.trim(), done: false };
  store.push(todo);
  return { ...todo };
}

export function resetTodos() {
  store.length = 0;
  nextId = 1;
}
```

新建 `apps\api\todos\todos.test.mjs`：

```js
import { test, beforeEach } from "node:test";
import assert from "node:assert/strict";
import { listTodos, addTodo, resetTodos } from "./todos.mjs";

beforeEach(resetTodos);

test("listTodos 初始为空数组", () => {
  assert.deepEqual(listTodos(), []);
});

test("addTodo 返回契约字段 id/title/done", () => {
  const todo = addTodo("写周报");
  assert.deepEqual(Object.keys(todo).sort(), ["done", "id", "title"]);
  assert.equal(todo.done, false);
});

test("addTodo 拒绝空标题", () => {
  assert.throws(() => addTodo(""), /title 不能为空/);
  assert.throws(() => addTodo("   "), /title 不能为空/);
  assert.equal(listTodos().length, 0);
});
```

### 5.3 故意犯错④：顺手改了契约

实现时你发现契约漏了排序，于是顺手在 `spec\openapi.yaml` 末尾加一行注释——这是多 Agent 项目里最常见的破坏方式。加上它，然后提交：

```
git add -A
```

```
git commit -m "feat(api): 待办列表与新增"
```

```
node scripts/orchestrator.mjs manifest --task API-010
```

`manifest` 就已经预警了：

```json
{ "changedFiles": ["apps/api/todos/todos.mjs", "apps/api/todos/todos.test.mjs", "spec/openapi.yaml"],
  "outOfScope": ["spec/openapi.yaml"] }
```

```
node scripts/orchestrator.mjs verify --task API-010
```

去 `artifactDir` 填好 `acceptanceEvidence` 和 `handoff.md`，然后：

```
node scripts/orchestrator.mjs complete --task API-010 --agent api-01
```

```
错误: 证据未通过，任务保持 working：
  - 改动越界，不在任务 paths ["apps/api/todos/**"] 内: ["spec/openapi.yaml"]
  - 改动超出 role=api-worker 的所有权范围: ["spec/openapi.yaml"]
  - 改动命中 role=contract-owner 的单写者专属路径，必须由其处理: ["spec/openapi.yaml"]
```

三层规则各说各的：任务范围、角色范围、单写者。撤回它——契约改动应该另开一个 contract-owner 任务：

```
git checkout main -- spec/openapi.yaml
```

```
git commit -m "revert(spec): 契约改动交回 contract-owner"
```

```
node scripts/orchestrator.mjs manifest --task API-010
```

```
node scripts/orchestrator.mjs verify --task API-010
```

`manifest` 会重置 `acceptanceEvidence` 里新增的条目吗？不会，已填的会保留，但**每次 `manifest` 后都要再确认一遍**。确认无误后：

```
node scripts/orchestrator.mjs complete --task API-010 --agent api-01
```

### 5.4 被驳回一次

【目录：`orchestrator-demo-api`】



修复流程和第一轮完全一样：重新 `claim-task` → 改代码 → `git commit` → `manifest` → `verify` → 填证据 → `complete` → `review approve`。

## 8. 速查

Worker 一轮的肌肉记忆：

```
claim-task → 改代码(只在自己 paths 内) → git commit → manifest → verify → 填证据+handoff → complete
```

常用命令（都在项目目录或 worktree 里执行）：

```
node scripts/orchestrator.mjs status                      总览：谁在做什么、卡在哪
node scripts/orchestrator.mjs next                        能派什么 + 每个跳过的原因
node scripts/orchestrator.mjs show --task <ID>            单任务全量事实（恢复入口）
node scripts/orchestrator.mjs validate                    控制面体检，进 CI
node scripts/orchestrator.mjs recover --stale-minutes 45  回收超时 + 报告滞留
node scripts/orchestrator.mjs archive --message "第 N 轮"  给控制目录留 Git 快照
```

嫌命令长，可以在**当前终端**加个别名（换终端要重设）：

```
doskey orc=node scripts\orchestrator.mjs $*        :: cmd
```

```
function orc { node scripts/orchestrator.mjs @args }    # PowerShell
```

```
alias orc='node scripts/orchestrator.mjs'               # git-bash
```

**重来一次**：删掉 `orchestrator-demo`、`orchestrator-demo-control` 和三个 worktree 目录，重跑第 0 步。

## 9. 搬到真实项目

1. 把 `control\`、`docs\`、`prompts\`、`scripts\`、`templates\`、`AGENTS.md` 复制进你的仓库（已有 `AGENTS.md` 就合并内容，别覆盖）。
2. 改 `control\agents.json` 的 `verifyCommands` 为项目真实命令——默认值会**故意失败**，防止空跑。
3. 改 `control\ownership.json`：`paths` 是可改范围，`exclusive` 是单写者范围（契约、共享类型、迁移、CI 放这里）。
4. 写 `control\backlog.json`：每条任务必须有 `paths` 和可验证的 `acceptanceCriteria`，否则 `validate` 不过。
5. 在仓库根目录跑一次 `node scripts/orchestrator.mjs init-runtime --path <仓库外目录>`，把 `validate` 接进 CI。
6. 三个 Agent 会话分别喂 `prompts/coordinator.md`、`prompts/worker.md`、`prompts/reviewer.md`。

## 附录：什么时候才需要 `AI_CONTROL_ROOT`

指针文件 `control/RUNTIME.json` 记的是**本机绝对路径**，所以下面几种情况要显式设环境变量：

- Agent 跑在另一台机器或容器里。
- 多个仓库共用一个控制目录。
- CI 里 checkout 的是干净仓库，没有指针文件。
- 你想临时指向另一个控制目录做实验。

设法（当前终端有效）：

```
set AI_CONTROL_ROOT=D:\Project Code\orchestrator-demo-control
```

```
$env:AI_CONTROL_ROOT = "D:\Project Code\orchestrator-demo-control"
```

```
export AI_CONTROL_ROOT="/d/Project Code/orchestrator-demo-control"
```

三条分别对应 cmd、PowerShell、git-bash，**别混用**——截图里那个 `'export' is not recognized` 就是在 cmd 里用了 bash 的写法。

用 `status` 确认当前指向哪：`controlRoot` 是你的 `-control` 目录、`bootstrapMode: false`，就对了。
